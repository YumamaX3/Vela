## 2. 🚨 Headline — GHSA-pjm4-8fpg-f9p6: Vela is vulnerable

Upstream commit `92259214` — *"fix(security): require proof that x-9r-real-ip came
from the socket (GHSA-pjm4-8fpg-f9p6)"* — is a security advisory fix. **Vela carries
the hole it patches.** Verified evidence in Vela's current tree:

| Check | Vela state | Verdict |
|-|-|-|
| `src/lib/auth/trustedPeer.js` (the fix) | absent | 🔴 |
| `custom-server.js` peer-token (`NINEROUTER_PEER_TOKEN` / `x-9r-peer-token`) | 0 matches | 🔴 |
| `package.json` `start` | plain `next start --port 32060` — custom-server.js never loads | 🔴 |
| `dashboardGuard.isLocalRequest` | trusts `x-9r-real-ip` **unconditionally** | 🔴 |
| `keyGate.extractClientIp` | trusts `x-9r-real-ip` unconditionally (upstream has no keyGate — this is Vela's own surface) | 🔴 |

### The hole, precisely

`x-9r-real-ip` is only trustworthy when **custom-server.js** stamps it from the TCP
socket and strips attacker-supplied copies. But Vela's `npm start` runs plain
`next start` — no custom-server in front — so the header arrives **as the client
sent it**. A remote caller sets `x-9r-real-ip: 127.0.0.1` and poses as local.

### The concrete attack chain on Vela

1. Attacker sends `x-9r-real-ip: 127.0.0.1` → `isLocalRequest()` returns true
   (Origin header is optional and simply omitted).
2. Looking local **skips the forced password change** on the login route
   (`mustChangePassword` requires `!isLocalRequest`) — and Vela lacks upstream's
   second fix (remote default-password login 403), so if the dashboard still runs
   the default password `123456`, the attacker logs in from anywhere and gets a JWT.
3. Local + JWT satisfies `canAccessLocalOnlyRoute` → every `LOCAL_ONLY_PATHS` entry
   opens: `/api/auth/reset-password`, `/api/tunnel/enable|disable`,
   `/api/tunnel/tailscale-*`, `/api/mcp/*`, `/api/headroom/*`,
   `/api/cli-tools/cowork-settings`, `/api/cli-tools/antigravity-mitm`,
   `/api/oauth/cursor/auto-import`, `/api/oauth/kiro/auto-import`.
4. Bonus surface on Vela specifically: under plain `next start`, spoofing
   `x-9r-real-ip` also defeats **key IP allowlists** at the `/v1` gate
   (`keyGate.extractClientIp` trusts the same header). Vela's spoofed-local does
   *not* bypass the key requirement itself — the gate runs regardless of locality —
   but an allowlisted key's IP scope becomes meaningless without socket stamping.

**Exposure today:** Vela runs on a LAN/tailnet host, mostly `npm run dev`
(custom-server absent, but dev-local). The moment `npm start` faces any untrusted
network — or the tunnel features ship — this is remotely exploitable. Severity: **high**.

### How upstream fixed it (commit 92259214 anatomy)

| Piece | What it does |
|-|-|
| `src/lib/auth/trustedPeer.js` (new) | `hasTrustedPeerHeaders(request)` — true only if `process.env.NINEROUTER_PEER_TOKEN` is set and `x-9r-peer-token` header matches it |
| `custom-server.js` | generates a per-process secret (`crypto.randomBytes(24)`), exports it as `NINEROUTER_PEER_TOKEN`, stamps `x-9r-peer-token` + `x-9r-real-ip` on the internal forward — so only the socket-stamper can prove the header's provenance |
| `dashboardGuard.isLocalRequest` | trusts `x-9r-real-ip` **only when `hasTrustedPeerHeaders` proves it**; Host fallback confined to dev; **fail-closed in prod**; IPv6 loopback parsing fixed |
| `package.json` | `start` rerouted through `custom-server.js` — production always gets socket-stamped IPs |
| `scripts/copy-standalone-assets.mjs` | copies `custom-server.js` into the standalone build so it ships |

### Vela port plan (Vela-specific hardening included)

1. Add `src/lib/auth/trustedPeer.js` (upstream's, verbatim).
2. `custom-server.js`: per-process peer token + stamp both headers (upstream's).
3. `dashboardGuard.isLocalRequest`: gate header trust on `hasTrustedPeerHeaders`
   (upstream's), keep the documented dev Host fallback.
4. **Vela-only:** `keyGate.extractClientIp` must also require peer-token proof
   before trusting `x-9r-real-ip` — upstream has no key gate, so this surface is
   ours alone. `resolveClientIp`'s internal-key loopback-Host fallback stays (it
   only ever loosens keys already pinned loopback).
5. `package.json`: route `start` through `custom-server.js` (preserve PORT=32060
   semantics); extend `copy-standalone-assets.mjs` to ship it.
6. Tests: spoofing regressions in `tests/unit/dashboard-guard.test.js` + new
   keyGate spoofing cases in `tests/unit/apikey-gate-stages.test.js`.

Milestone Tide: a security fix is a big change → **0.6.03 → 0.6.10**.

## 3. Second security commit — also missing from Vela

`8a527fec` — *fix(security): SSRF guard on search baseUrl, default-password remote
login, and request-details redaction*:

- `/v1/search` `resolveBaseUrl` gains an SSRF guard (attacker-controlled URL could
  otherwise make the gateway fetch internal hosts).
- Remote login while still on the default password → **403** (Vela currently only
  flags `mustChangePassword`, and the spoof above defeats even that flag).
- Request-details endpoint redacts sensitive fields.

Port together with the GHSA fix — they are one security wave.

| Heat | Files | Why it burns |

**Strategy:** do not bulk-merge. Port the security wave first (small, surgical,
test-backed). Feature/provider updates cherry-pick cleanly for the most part
(provider registry files are append-only), but the 35 overlap files need
case-by-case resolution with Vela's rebrand and key-governance preserved.
