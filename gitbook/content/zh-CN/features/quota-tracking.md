# 配额跟踪与用量监控

Vela 为一切保留收据。本页讲的是读懂这些收据：每项额度还剩多少、何时重置、钱流向哪里，以及如何给它设置硬性上限。

---

## 概览

- **实时消耗** —— 每次请求、每个模型、每把密钥的 token 与成本
- **配额与剩余** —— 每个提供商的额度已用多少
- **重置倒计时** —— 窗口何时再次打开
- **成本估算** —— 依据 Vela 内置的费率计算
- **预算上限** —— 按 API Key 的硬性停止
- **历史** —— 今天、7、14、30、60 天，或全部时间

---

## 仪表盘的各个房间

```
配额       按提供商的额度与重置时间
用量       按周期、模型、组合和密钥的请求、token 与成本
日志港     请求账本，用于你需要查看单次请求时
```

### 配额页面显示什么

对于每个已连接的提供商，一行包含：

- **已用 / 总量** —— 当提供商公布限额时，以进度条和百分比呈现
- **重置** —— 到下一个窗口的倒计时
- **到目前为止的成本** —— 针对按量计费的通道

配额数据来自各提供商。在提供商不公布可用数字的地方，Vela 会显示它能测量的内容（你自己的用量）并说明这一点，而不是凭空编造一个百分比。

### 用量页面显示什么

- 所选周期内的请求数与 token 数
- 按模型、组合和 API Key 拆分的成本
- 究竟是哪个模型在应答（通过 **Routed by Combo**）

---

## 按请求跟踪

每次请求都会连同其模型、token 计数、耗时、结果和成本被记录。当账单让你措手不及时，你就在这里找到造成它的那次请求。

如果你想要完整的请求与响应体，请开启 `ENABLE_REQUEST_LOGS` —— 它默认关闭，因为它体积庞大，且包含你发送的一切。

---

## 不同配额形态的行为

配额并不是同一种东西。提供商使用好几种形态，它们的重置方式各不相同：

| 形态 | 典型提供商 | 重置方式 |
|-------|-------------------|---------------|
| **滚动窗口** | Claude Code、Codex | 窗口滑动；旧用量随时间流逝而释放，额度回归 |
| **固定每日** | 某些低价通道 | 在提供商的时区中某个固定钟点 |
| **每月** | Copilot、各类套餐 | 在某个日期，通常是 1 号或你的账单日 |
| **按量额度** | GLM、MiniMax、大多数 API Key | 从不"重置" —— 它是一个余额 |

实际后果是：在滚动窗口上，等一小时可能就够了；在固定每日窗口上，睡一觉可能值得；在余额上，只有付钱才有帮助。

## 成本估算

Vela 依据 `open-sse/providers/pricing.js` 估算成本。这里最要紧的两个费率：

| 模型 | 输入 /1M | 输出 /1M |
|-------|-----------|------------|
| `glm/glm-4.7` | $0.60 | $2.20 |
| `minimax/MiniMax-M2.1` | $0.30 | $1.20 |

因为输出价格是输入的三到四倍，一段输出密集的对话远比一段长提示配短回答要贵。当某个数字看起来偏高时，先看拆分，再去找故障。

估算就是估算：提供商可能在 Vela 的费率表跟上之前更改零售费率。你的账单才是权威。

## 预算与上限

有两种不同的控制，它们的行为也不一样。值得弄清楚你打开的是哪一种。

### 按密钥的预算（硬性停止）

```
仪表盘 → 端点与密钥 → 创建密钥（或编辑现有密钥）
  token 预算:  每日 / 每周 / 每月 / 每年
  支出上限:    以货币计
```

当某个密钥触达上限时，经由该密钥的请求会被拒绝：

```
HTTP 429 — "Monthly spend cap exceeded: $20.00 of $20.00 used (budget_exceeded)"
```

这是拒绝，不是重定向。Vela 不会为了留在上限之内而把你转到更便宜的模型；它会停下，因为"停下"正是你所要求的。

### 网关预算（软阈值与硬上限）

用量预算可以设置在网关、密钥或模型范围，带日、周或月的窗口。它们会在 50%、80% 和 100% 时发出告警，并在越过硬上限后直接拒绝 —— 附带指明范围的代码。

### 与回退的区别

组合在请求**失败**时转向下一个模型。预算在你**花得够多**时拒绝。两者都不会意外发生，也都不会替你猜测。

## 通过 API 读取你自己的用量

仪表盘读取的正是你也能读取的端点：

```bash
# 用量摘要
curl "http://localhost:32060/api/usage/stats?period=7d" \
  -H "Authorization: Bearer <key>"

# 随时间变化的请求指标（用于图表）
curl "http://localhost:32060/api/usage/metrics/timeseries?period=7d" \
  -H "Authorization: Bearer <key>"

# 预算定义
curl "http://localhost:32060/api/usage/budgets" \
  -H "Authorization: Bearer <key>"
```

有效周期：`today`、`24h`、`7d`、`14d`、`30d`、`60d`、`all`。这些与仪表盘周期选择器使用的窗口相同，因此对每周脚本很方便。

## 告警

当预算越过某个阈值时会产生告警记录，可以投递到仪表盘横幅、Discord webhook 或 n8n webhook，取决于你的配置。

月度摘要邮件不是 Vela 会自行发送的东西；如果你想要，上面那套 API 加一个 cron 任务就是一个十行脚本。

## 良好习惯

### 1. 每天看一眼

**配额** 页面只需十秒。它对你这一周的说明，胜过任何效率工具。

### 2. 给无人值守的密钥设置上限

智能体、后台任务、任何会循环的东西。一次设置的上限，胜过一份只读一次的账单。

### 3. 给每个工具各自一把密钥

这样按密钥的用量报告才真正有意义。

### 4. 无聊的工作优先用更便宜的模型

一个把"写一条提交信息"首先交给 GLM 的组合，比把它送到 Opus 的组合便宜得多，而且回答同样好。

### 5. 把估算当作估算

它们源自公布的费率和 token 计数。它们足够精确到可以用来做预算，但不够精确到用来和账单争辩。

## 故障排查

### 配额显示已用，但请求失败

提供商可能正在施加 Vela 看不见的限制（账户级上限、每分钟速率限制）。配额数字是向导，不是承诺。试试别的模型，或查看提供商的状态页。

### 成本看起来不对

1. 检查费率：**低价提供商** 列出了 Vela 内置的那些。
2. 检查拆分 —— 输出 token 占主导。
3. 检查模型 —— `-highspeed` 和更大的变体更贵。
4. 如果提供商改了价格，在费率表更新之前，估算会有偏差。

### 重置倒计时像是卡住了

刷新页面；配额数据在加载时获取。如果倒计时对于一家公布了重置时间的提供商来说是错的，那是 Vela 正在显示的上游细节，而非它计算出来的。

### 触达预算，但我想继续

在 **端点与密钥** 中编辑该密钥的预算，或换用另一把密钥。那次拒绝正是上限在履行它的职责。
