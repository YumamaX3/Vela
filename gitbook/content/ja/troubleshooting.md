# トラブルシューティング

Velaの問題のほとんどは、5つのうちのどれかです: 動いていない、キーが違う、モデル名が存在しない、プロバイダーのクォータが尽きた、あるいはあいだのネットワークが邪魔をしている。

このページは、あなたが出会いそうな順に扱います。直し方はどれも、一分以内に確かめられるものです。

---

## まず、すべての半分を解く2つの確認

```bash
# 1. Is the gateway alive?
curl http://localhost:32060/api/health
# → {"ok":true}

# 2. Can it see any models?
curl http://localhost:32060/v1/models -H "Authorization: Bearer <your key>"
```

- **まったく答えがない** → 動いていないか、別のポートにいます。[接続が拒否される](#connection-refused)を見てください。
- **答えはあるが、モデルの一覧が空** → プロバイダーが接続されていません。[モデルが見つからない](#model-not-found)を見てください。
- **`401`** → キーです。[APIキーが無効](#api-key-invalid)を見てください。
- **`429`** → クォータか、レート制限か、あなたが設定した予算です。[レート制限](#rate-limiting)を見てください。

---

## 「Language model did not provide messages」

**意味:** リクエストがプロバイダーに届き、空か拒否で返ってきた。

**原因:** クォータの尽き、切れた接続、あるいは上流がもう供さないモデル。

**直し方:**

1. **割り当てを確かめる** — **Quota**で、このプロバイダーの残量とリセットのカウントダウンを。
2. **接続を確かめる** — **Providers**: 期限切れのOAuth接続は、注意を要すると表示されます。切断し、もう一度接続してください。
3. **コンボを使う** — 調査しているあいだ、次のモデルが答えるように:

   ```
   cc/claude-opus-5 → glm/glm-4.7 → if/qwen3-coder-plus
   ```

## レート制限

**意味:** `429 Too Many Requests`、しばしば再試行のヒントつき。

**原因:** サブスクリプションの窓が閉じている、バーストで毎分の制限に当たった、あるいはキーの予算の上限に達した。

**直し方:**

1. **応答のコードを読む。** `budget_exceeded`のコードは、あなたが上限を決めて達したという意味です — **Endpoint & Key**で編集してください。ただのレート制限は、待つか切り替えるかです。
2. **リセットのカウントダウンを確かめる** — **Quota**で。
3. **負荷を散らす** — **設定 → ルーティング → ラウンドロビン**で、同じプロバイダーの複数のアカウントに。
4. **サブスクリプションが回復するあいだ、格安のレーンを使う**: `glm/glm-4.7`、`minimax/MiniMax-M2.1`。
5. **自分のコードでバックオフつきに再試行する** — 再試行のヒントに従い、叩き続けないこと。

## OAuthトークンの期限切れ

**意味:** `Unauthorized`、あるいは昨日は動いていて今日は動かないプロバイダー。

**原因:** 更新が失敗した(プロバイダーがセッションを無効にした、更新の途中でネットワークが落ちた、あるいはアカウントのパスワードを変えた)。

**直し方:**

1. **再接続する:** **Providers → [provider] → Disconnect → Connect**へ行き、ログインをもう一度最後まで。
2. プロバイダーが複数のアカウントを示すなら、正しいものが有効か確かめてください。
3. ヘッドレスのサーバーなら、プロバイダーが許すなら、別のマシンでOAuthの流れを完了し、コールバックを貼り付け直してください。

## 接続が拒否される

**意味:** `ECONNREFUSED`、あるいは「Cannot connect to localhost:32060」。

**原因:** Velaが動いていない、別のポートにいる、あるいはファイアウォールが邪魔をしている。

**直し方:**

```bash
# Start it
vela

# or, if it is running elsewhere
vela --port 8080

# Is anything listening?
lsof -i :32060            # macOS / Linux
netstat -ano | findstr :32060   # Windows
```

ツールのベースURLが`/v1`で終わるか確かめてください — それがなければ`http://localhost:32060`はダッシュボードに届き、APIには届きません。

ほかのマシンから接続しているなら、デフォルトの束ねが`0.0.0.0`でもファイアウォールがなお妨げうること、そして`--host 127.0.0.1`で起動したならそのマシンだけが届けることを思い出してください。

---

## ダッシュボードが開かない

**意味:** `http://localhost:32060/dashboard`が空白か、回り続けるか、届かない。

**原因:** ポートが取られている、Velaが落ちた、あるいはブラウザのキャッシュが古い。

**直し方:**

1. **プロセスを確かめる** — `vela --log`が出力を映します。何も動いていなければ、起動してください。
2. **ポートを確かめる**:
   ```bash
   lsof -i :32060                               # macOS / Linux
   lsof -ti:32060 | xargs kill -9               # stop the squatter
   netstat -ano | findstr :32060                # Windows
   taskkill /PID <PID> /F
   ```
3. **プライベートウィンドウを試す** — キャッシュか拡張機能を排除するため。
4. **ほかのマシンから?** それはパスワードの門です。ローカルのアクセスは開いていて、遠隔のアクセスは、**設定 → アクセス**でパスワードを設定するまで拒否されます。

---

## モデルが見つからない

**意味:** `404`、あるいは「model not found」。

**原因:** 打ち間違い、接続されていないプロバイダー、あるいは上流で名前を変えられたモデルID。

**直し方:**

1. **ゲートウェイに何を持っているか尋ねる:**
   ```bash
   curl http://localhost:32060/v1/models -H "Authorization: Bearer <key>"
   ```
2. **形式を確かめる** — `prefix/model`、たとえば`glm/glm-4.7`であって、単独の`glm-4.7`ではありません。
3. **そのモデルの属するプロバイダーを接続する。**
4. **モデルの一覧は動く。** 先月は動いて今日は動かないなら、プロバイダーがIDを退役させたのでしょう。上の一覧から現在のものを選んでください。

---

## 応答が遅い

**意味:** リクエストのストリーミングがなかなか始まらない、あるいはタイムアウトする。

**原因:** プロバイダーの遅延、大きなコンテキスト、無料枠の優先度、あるいはストリームをバッファリングするプロキシ。

**直し方:**

1. **より速いモデルを試す** — `cc/claude-haiku-4-5-20251001`、`minimax/MiniMax-M2.5-highspeed`、`qwen/qwen-turbo`。
2. **コンテキストを減らす** — 履歴を削り、リポジトリではなく関係するファイルを送る。
3. **無料枠は負荷のときに遅い**、それは設計です。大事なら、レーンを上げてください。
4. **プロキシの背後?** ストリーミングにはバッファリングを切る必要があります:
   ```nginx
   proxy_buffering off;
   proxy_read_timeout 86400;
   ```
5. **ネットワークを確かめる** — あなたとプロバイダーのあいだの。

## APIキーが無効

**意味:** `401 Unauthorized`。

**原因:** 間違ったキー、切れた貼り付け、消されたキー、あるいは`REQUIRE_API_KEY`がオンのときにキーを送っていない。

**直し方:**

1. **新しいキーを作る:** **Endpoint & Key → Create Key**。キーは作成時に一度だけ表示され、ハッシュとしてだけ保存されます。古いものを探し出す方法はありません。
2. **形式を確かめる** — Velaのキーは`vela-v1-<id>-<checksum>`の形です。古い`sk-...`風のキーはこの形式より前のもので、もう受け入れられません。
3. **ヘッダーを確かめる** — `Authorization: Bearer <key>`、よけいな空白や改行なしで。
4. **試す:**
   ```bash
   curl http://localhost:32060/v1/models -H "Authorization: Bearer <key>"
   ```
5. **キーに範囲があるなら**、求めているモデルがその範囲のなかにあるか確かめてください。

## Velaからではなく、プロバイダーからの「Invalid API key」

**意味:** Velaはあなたのキーを受け入れたが、上流がプロバイダーの資格情報を拒否した。

**直し方:**

1. **Providers**で、プロバイダーのAPIキーかログインを確かめ直してください。
2. 上流のアカウントにクレジットがあるか確かめてください。
3. 露出したかもしれないなら、上流のキーを作り直してください。

---

## 昨日はすべて動いていた

これは最もよくあるトラブルの形で、ほとんどは上流です:

- 無料枠が制限を締めた
- プロバイダーがモデルIDを退役させた
- OAuthセッションが無効にされた
- プロバイダーに障害があった

プロバイダーのステータスページを確かめ、**Providers**で再接続し、回復するまでコンボに運ばせてください。
